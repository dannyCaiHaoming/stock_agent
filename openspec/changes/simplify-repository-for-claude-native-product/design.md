同一产品主线程在核心正反依赖及必要证据齐后准备CIO任务，完整消费报告及必要事实，自主综合，提交触发原fixture Risk，完整回读risk_status/risk_support/fixture_decision与最终产物。保留实际主线程身份、消费、Risk、回读和advisory_only=true，不建CIO子Agent、Risk执行器或主观评分。

#### 5.1.4 独立冻结Market切片

新Market作者通过正常入口实际读取授权计算目录，自主选择结果并完整消费所需血缘，合法提交，专业及父线程双方按精确回执完整回读。核对角色/方法、11工具、实际模型、计算值/窗口/单位/方向及限制。它不消费fixture结论、不参与fixture CIO，不认证完整八维或MRVL来源至CIO链。合法不足报告若缺少实际尝试依据，仍不能证明完成必需研究。

#### 5.1.5 内容与操作可用性

在现有验收记录分别裁定四份完整报告的依据、数值/期间/单位、方向、重要反证、输入性质和限制。核心错误为FAIL，无稿或未完整读为NOT_REVIEWED；不回写原报告状态，不以Schema或BLOCKED替代成功，不匹配旧答案或启用自动评分/额外Reviewer模型。

核心与Market分别验证一次稳定交付后无需开发逐步纠错。正常权限批准、既定证据核对和产品主线程职责不算开发干预。诊断成功不是研究成功；两部分实际满足后才有限完成，不声称统计稳定性或Promotion。

有项目缺陷证据才更新实际受影响设计/接口，在既有接缝最小修补与聚焦检查，必要加载成立后使用。当前定位没有这样的证据，记录无需代码修改，按上述合并顺序进入唯一正常Market执行，不再追查唯一底层根因或增加付费预检。真实安全/权限/来源失败、必要宿主能力已知不可得或实际目录拒绝仍停止，不绕Schema或正确服务端门禁。确定性验证只证明自己的层级，正式验收仍须实证原生使用。

## Risks / Trade-offs

- 诊断可能仍无法形成实际调用 → 记录未解决及首个分歧，停止，不把无法诊断推定为服务端缺陷或无资料。
- 干净作者可能成功但不能解释旧失败 → 新任务独立验收，旧失败保持；不将更换上下文冒称代码修复或统计稳定性。
- 诊断指引污染正式研究 → 诊断与正式作者分离，后者只接收正常稳定交付，不交选定指标/引用/结论。
- 原始Schema不可得 → 优先实际调用及宿主必要观察；不把可选底层取证当唯一入口，也不豁免真实模型、工具及隔离证据。
- 宿主加载或修订能力不足 → 报告具体外部依赖，不另造后端或擅自操作进程。
- 多Change共享dirty工作树 → 只改已授权hunk，无法分离、敏感信息或检查失败时停止相关发布。
