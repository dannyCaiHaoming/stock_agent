## Context

动机与范围见 [Proposal](proposal.md)。根开发规则已有安全、授权和条件读取边界，开发流程已有聚焦检查、证据复用与人工收尾要求，但未完整约定需求调整落盘及唯一交接摘要。规划时根 `CLAUDE.md` 不存在；Claude Code 支持 `AGENTS.md` 和 `@` 文件导入，因此薄入口用于明确单一来源，不是另造加载器。

现有 `tests/test_development_workflow.py`、`tests/test_agent_package_demo_workflow.py` 和 `tests/test_governance.py` 包含本地链接、开发/产品隔离、Demo/真实 Smoke 与发布边界检查。部分根文档和测试已有其他任务的未提交修改；不得回退或用 HEAD 全文覆盖。治理主规格的原生产品入口条款另由其他 Change 处理，本次只加 [开发治理约束](specs/three-plane-governance/spec.md)，不修改那些条款。

## Goals / Non-Goals

**Goals:**
- 用现有文档形成“目标 → 当前规划 → 实施 → 实际验证 → 状态/交接”的最小闭环，避免要求用户自行补写工程规格。
- 让后续会话能从 Tasks 找到当前范围、授权和下一步，同时准确定位规格及原始证据。

**Non-Goals:**
- 不新增自动状态同步、任务数据库、证据 Schema、Hook 或校验平台；规则是上下文约束，不宣称程序强制执行。
- 不批量迁移历史 Tasks、不处理其他 Change 的未完成项、不将本次文档通过解释为其验收豁免；其余排除范围沿用 Proposal。

## Decisions

### D1：根原则、流程细则与宿主入口分别负责

| 文件 | 本次修改职责 |
| --- | --- |
| 根 `AGENTS.md` | 整合目标/最小方案、调整与恢复读取、稳定完成线、唯一状态、验证/历史真实性及结果报告；保留全部安全和授权边界 |
| `docs/development/workflow.md` | 说明调整适用范围、文档职责、普通修复例外、同步节点、短状态模板和验收分层；合并重复条款 |
| 新根 `CLAUDE.md` | 标题、独立 `@AGENTS.md` 导入及一句共享规则说明，不复制规则或产品职责 |

选择现有文件而非新增流程索引/结果文件，减少平行维护。根规则不保存本 Change 的状态或固定开发顺序；常用自检、显式 Demo/Smoke、受限历史维护和旧入口退役提示不因精简被移除。

### D2：只更新实际改变的规划，不把普通修复变成重新立项

需求调整先获得相应规划修改授权，再更新受影响 Specs、Design、Tasks并记录原因；目标/范围改变加改 Proposal。未确认讨论不自动写入。恢复原要求的普通错误可在有效 apply 范围持续修复，无须重写无关规划。改变安全、验收或范围不得借“普通修复”跳过批准。选择影响驱动更新，拒绝“每次调整四文件全部重写”和“聊天已说就直接实现”两种极端。

### D3：Tasks 只保留一个当前摘要，证据仍在原位置

在开发流程提供普通 Markdown 模板，置于 Tasks 前部，字段为：更新、范围与授权、完成与剩余、验证与验收、阻断与未知、下一步。引用任务编号、规划段落和已有证据，不复制全文或把模板当授权。承载事实的契约仍保留 `source_id`、`as_of`、`retrieved_at`，不为模板新增技术 Schema。

按有意义节点同步，不要求每次工具调用写状态。旧 FAIL/UNKNOWN/NOT_RUN按原时点保留；新证据可解除当前问题而不回签旧运行。其他文档可记录设计、验收依据和历史，但以链接取得当前进度。选择已有 Tasks，而非新增 status.md/JSON或平行 handoff 文件；不改其他现行/历史 Change 来追求格式一致。

### D4：验收限定于本次文档与静态结构

复用三个已定位的确定性测试模块，优先只在 `tests/test_development_workflow.py` 增加薄入口的正式导入、目标与必要文档结构检查。只检查稳定结构/边界，不绑定整段固定中文措辞，不用关键词命中宣布 Agent 遵循。现有 Demo/治理测试若因职责整理受影响，仅定点对齐，不删安全负例或扩大执行入口。

开发流程“每次两种实际交付路径”收敛为受影响实际路径；两条均受影响或既定规格明确要求时仍覆盖两条，不豁免原要求。证据定位/既有版本锁保留，但不将“完整 hash”推导为每轮制作全仓快照。文档链接/格式、限定差异和本 Change strict一起验证，结果直接记 Tasks，不新增 acceptance.md、JSON或日志副本。

不启动 Demo、产品或模型会话；本次不改变产品加载/启动能力。静态导入通过不证明本机实际加载，结构检查不证明行为遵循、权限强制、研究质量、token节省或耗时改善。此限制明确报告，不作为自动追加真实运行的理由。

### D5：保持并行工作与批准边界

apply前重读最新目标文档、测试及本 Change四类规划，保留已有修改，按授权内容定点编辑。不同 hunk不自动证明资源绑定安全；如目标文件被明确冻结或存在无法安全分离的共享修改，只暂停相关项并报告最小交接需求，不重排另一任务。

propose阶段只写必需规划并停止；规划呈现后收到新的明确 apply消息才实施。实施/验证后先交付目标对应结果并等待一次人工完成批准，再依既有流程同步本次主规格、归档与限定发布；不把计划批准等同完成批准，不在此改变外部 Skill 的边界。

## Risks / Trade-offs

- [规则变长仍可能增加负担] → 替换/合并相关旧条款，细则留现有开发流程，不复制整份正文、不追加全量专项读取。
- [唯一摘要被误当唯一事实或新授权] → 明确摘要只是当前进度/交接入口，引用规格、实际批准和原始证据，冲突先核对而不自动取更宽权限。
- [薄根入口可能成为产品会话祖先上下文] → 保留根“不充当 CIO”和产品阶段授权边界，不导入 `product/CLAUDE.md`，不改产品运行面。
- [静态检查无法证明长期行为改善] → 只交付规则/结构的检查结论，实际遵循与加载未观察则如实说明，不虚构成效或新增模型验收。
- [共享文件已有修改] → 基于最新磁盘内容编辑并限定审阅，无法安全归属时停止相关发布，不回退用户现场。

## Migration Plan

获新 apply后依次整合根规则、流程细则/模板、薄根入口与受影响静态检查；完成聚焦验证并更新 Tasks。后续创建/恢复 Change时遵循新约定，历史记录不批量改写。需撤销本次修改时也仅处理本次差异，保留其他工作；不使用全仓 reset、清理私人材料或重签历史证据。收尾按既有人工批准与限定归档/发布流程执行。
