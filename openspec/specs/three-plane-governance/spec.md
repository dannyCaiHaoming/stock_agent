# three-plane-governance Specification

## Purpose

建立开发、产品运行和学习优化三套相互隔离但可审计衔接的控制边界，使研究系统的运行权限、变更权限和版本晋升责任始终明确。

## Requirements

### Requirement: 系统必须区分三个治理平面
系统 SHALL 将开发控制面、产品运行面和学习优化面定义为不同的指令域，并分别规定其可访问资源、允许操作和禁止操作。

#### Scenario: 运行时加载产品规则
- **WHEN** 用户启动一次 portfolio council 运行
- **THEN** 系统仅向运行时 Agent 应用产品运行面的指令和只读能力，不授予开发或生产修改权限

#### Scenario: 开发任务加载开发规则
- **WHEN** 开发 Agent 执行 OpenSpec、测试、评审或实现任务
- **THEN** 系统应用开发控制面规则，并将产品运行规则作为被实现和验证的契约而非开发权限来源

### Requirement: 开发与运行 Agent 必须物理区分
系统 SHALL 使用根级开发指令和 `dev_*` Agent 配置管理开发工作，并使用产品级指令和 `runtime_*` Agent 配置管理投资研究运行，二者不得共享可变生产权限。

#### Scenario: Runtime Agent 尝试修改产品
- **WHEN** runtime Agent 请求编辑 Skill、Agent 配置、Risk Policy 或程序文件
- **THEN** 系统拒绝该操作并在 Decision Trace 中记录权限违规

### Requirement: 能力必须先于 Agent 建立
任何新增 runtime Agent MUST 对应至少一个已定义完整输入、数据工具、推理方法、结构化输出和 Eval 的 Capability；系统不得仅为角色完整性创建空 Agent。

#### Scenario: 提议新增专业 Agent
- **WHEN** 开发者提议新增行业、宏观或技术分析 Agent
- **THEN** 评审必须验证其 Capability Contract 和相对现有架构的 Eval 增益，否则不得晋升

### Requirement: 生产版本必须通过人工晋升
Skill、Agent 配置、Schema、MCP Adapter 和 Risk Policy 的候选版本 MUST 经 OpenSpec、测试、回归评估和人工评审后才能成为产品运行面默认版本。

#### Scenario: 学习面提出改进
- **WHEN** 学习优化面生成 Improvement Proposal
- **THEN** 该建议保持为非生产候选，直到开发控制面完成规定的晋升流程

### Requirement: 开发指令必须按任务条件读取
根指令 SHALL 仅承载项目原则、常用入口、职责边界、完成标准、安全要求和专项文档的读取条件，默认中文并保留英文代码标识符及协议字段。流程、模型和验收细则 MUST 有明确且不重复的权威位置，不得要求所有任务完整读取全部专项文档。根指令 MUST 明确：开发自检在当前环境进行且不自动启动产品、模型或项目沙箱；真实 Smoke 与 Execution Replay 使用现有宿主 launcher；独立复核默认读取差异、规格及已有证据。底层运行模块不得被推荐为绕过宿主入口直接启动真实产品的默认方式。

#### Scenario: 普通开发与专项诊断
- **WHEN** 用户执行普通授权开发任务
- **THEN** 仅加载开发规则及该任务必需的专项内容，不因产品指令而获得 CIO 权限；仅在诊断、验收或归档等对应条件满足时读取相应细则

#### Scenario: 产品运行不触发开发收尾
- **WHEN** 用户调用产品 portfolio-council
- **THEN** 应用产品规则，不执行开发归档、Git 提交、推送或生产文件修改；保留 advisory-only、PIT、Evidence、Risk 和学习面禁止自动修改的安全要求

#### Scenario: 仅依靠根指令选择执行入口
- **WHEN** 开发者或 Reviewer 从根指令决定自检、真实产品运行或独立复核方式
- **THEN** 能明确区分当前环境确定性检查、宿主 launcher 和只读证据复核；不被引导自动启动 Council、旧 probe/preflight 或额外项目沙箱，缺少补跑授权时仅报告具体证据缺口

### Requirement: Change 验收必须依据差异限定且不替代晋升
开发流程 MUST 明确区分日常开发、Change 验收和候选版本晋升。日常开发 SHALL 使用受影响聚焦验证，不把完整测试、全量 Gate、生产批准或晋升证据作为每次修改/普通错误修复的默认前置。Change 验收 MUST 在验收前声明受影响范围、规格映射和证据复用依据，以版本、输入、依赖及底层执行证明判断适用性。仅对受影响且缺少有效证据的项目补测；修改产品运行加载或启动行为 MUST 提供受影响的真实 Smoke。仅开发文档及开发 Reviewer 规则改变时 SHALL 验证对应文档/配置，不因此启动产品 Smoke。

独立 Reviewer MUST 按当前评审目的、实际差异和对应规格复核，而非仅复述 PASS；普通开发复核不得默认要求生产晋升批准。候选晋升仍 MUST 独立满足既有完整测试、Eval/Regression、安全及人工晋升门禁。本规则不得豁免当前 Change 或主规格对安全与真实执行的明确要求，也不得因 Check 范围精简而自动关闭未完成任务。

#### Scenario: 未受影响证据复用
- **WHEN** 旧证据对应的能力、输入和依赖未受修改影响
- **THEN** 报告完整 hash、适用理由和局限并复用；历史 Replay/Ablation 只证明对应历史能力，不充当新候选晋升证据，不默认重跑 Calibration、Ablation、Promotion

#### Scenario: 旧 Change 已完成但不能晋升
- **WHEN** 旧 Change 获人工批准且候选为 NOT_PROMOTABLE
- **THEN** 保留两种结论，不要求旧候选 Promotion PASS 来启动下一项已授权工作；尚未完成的安全发布收尾仍须按原批准处理，不重开旧需求

#### Scenario: 发现越界或必须扩大验收
- **WHEN** 发现范围外问题、敏感信息，或现有明确规格与拟定有限验收有冲突
- **THEN** 记录对应依据与缺口并停止相关工作；先提出透明的流程调整供批准，不偷偷降低标准或自行扩展全量 Gate

#### Scenario: 日常开发只需聚焦验证
- **WHEN** 正在实现或修复授权范围内的一个开发步骤，未申请 Change 完成或版本晋升
- **THEN** 执行必要的受影响检查并继续；不因缺少发布级报告、人工晋升批准或全量产品运行而停止普通开发

#### Scenario: Reviewer 评审本次开发文档
- **WHEN** 复核范围仅为开发规则、Reviewer 配置和相关测试
- **THEN** 读取本次差异与有限证据，验证原安全边界和人工批准未被删除，不要求真实投资委员会、全量 Regression 或 Promotion PASS；报告只证明该范围

#### Scenario: 股票 Change 的验收仍未完成
- **WHEN** 开发流程小 Change 已通过，但股票 Change 缺少其明确要求的真实运行或研究质量证据
- **THEN** 股票任务仍保持未完成，按其原标准继续补齐，不能用开发规则通过代替股票研究验收

### Requirement: 功能验收与隔离保证必须如实区分
经明确人工批准，日常开发与功能验收 SHALL 与全进程隔离验收分开；全进程源码强制只读 MUST 保留 UNVERIFIED 和残余风险，排除在本 Change 完成保证之外，不影响原生权限、业务安全或独立生产晋升门禁。

#### Scenario: 范围批准不是完成批准
- **WHEN** 用户批准范围调整并接受残余风险
- **THEN** 同步批准与规格，但不自动关闭其他未完成任务、提升候选、归档或发布；历史运行仅按其版本和功能范围复用

### Requirement: 开发必须在已授权范围持续实施
开发 Agent MUST 在获得明确实施授权后持续推进本次范围内的未完成任务，阶段汇报 SHALL 作为进度消息而非结束任务或重新索取实施授权的理由。普通实现、路径、依赖定位或测试断言错误 MUST 在现有权限和范围内自行诊断、修复并执行受影响的聚焦验证，不得因每完成一个步骤就要求用户再次确认。此规则不得将仅诊断请求扩展成修改授权，不得突破模型次数、费用、来源访问或工具权限限制，也不得改写失败证据。

#### Scenario: 阶段汇报后仍有授权工作
- **WHEN** 一个实现阶段或聚焦测试完成，仍有安全且无依赖阻断的已授权任务
- **THEN** 报告该阶段结果并继续，不仅以“下一步可以做”结束任务等待用户回复

#### Scenario: 普通错误可在当前范围修复
- **WHEN** 发现类型、路径、导入或断言问题，处理无需新权限或范围变更
- **THEN** 自行修复并验证，保留真实失败记录，不放宽产品安全校验或通过补写证据伪装成功

#### Scenario: 存在真实阻断
- **WHEN** 后续工作需要未授予的权限、用户关键选择、超出现有范围或预算，或外部条件无法在现有约束内解决
- **THEN** 暂停受影响步骤并说明具体依据及最小用户动作；无依赖的其他已授权工作可以继续，不自动提权、扩大模型重试或改变规格

#### Scenario: 需要明确批准的流程阶段
- **WHEN** 尚未获得显式 apply 或人工完成批准
- **THEN** 保留对应批准边界，不把创建提案、阶段汇报、Reviewer PASS 或过去的范围批准当作本次实施或完成批准

### Requirement: 暂停 Change 与限定提交必须保留其他工作
用户要求暂停的 Change MUST 保留任务状态、未提交修改和历史证据，不归档、回退或将未完成项勾选完成。独立的小 Change MUST 仅提交其已审阅并批准的差异，文件重叠时以实际改动范围而非整文件归属区分；不能安全分离时 MUST 停止提交并报告。恢复顺序 SHALL 遵守用户指定的收尾条件，并重新读取生效开发规则与原 Change 产物。

#### Scenario: 小 Change 与股票修改共处工作树
- **WHEN** 工作树或同一测试文件中已有未完成股票 Change 的修改
- **THEN** 保留这些修改，不清理工作树；小 Change 提交不夹带股票代码、旧运行包或无关暂存内容，提交后明确列出仍未提交的工作

#### Scenario: 小 Change 完成后恢复
- **WHEN** 小 Change 已按人工批准规则完成同步、归档和限定 Git 收尾，用户已要求随后恢复原任务
- **THEN** 重新读取更新规则及原 Change 的 Proposal、Specs、Design、Tasks，从原未完成项继续，不新建替代股票 Change，不降低其验收标准或补写历史版本锁

### Requirement: MVP 开发授权不得被拆成逐步骤批准
用户明确批准 apply 后，开发 Agent SHALL 连续完成该 Change 既定任务、普通错误修复和聚焦确定性验证。仅当需要新增权限、执行破坏性操作、使用付费服务或凭证、改变已批准范围或安全契约、遇到无法自行解除的真实阻断，或准备最终归档与推送时，才 MUST 请求用户决定；阶段汇报、文件修改、普通测试失败和下一项任务不得单独触发批准。

#### Scenario: 实现过程中出现普通断言错误
- **WHEN** 修复不改变规格、权限、外部状态或安全边界
- **THEN** 开发 Agent 自行修复并继续聚焦验证，不暂停等待“继续”

#### Scenario: 准备归档并推送
- **WHEN** Change 任务与限定验收均完成
- **THEN** 开发 Agent提交完成摘要并等待一次明确人工完成批准，未获批准不归档或推送

### Requirement: Agent Package MVP 与候选晋升必须使用不同完成标准
`DEMO_SCAFFOLD` 的 Change 完成 SHALL 只证明 Agent Package 静态拓扑绑定、输入、只读 Tool Port、角色响应、数据传递、Risk 和最终输出可运行。独立 Reviewer、真实 LLM、语义评分、Replay、Regression、Calibration、Ablation 与 Promotion MUST NOT 成为该 Demo Change 的默认完成条件；当用户明确申请真实产品验收或候选晋升时，仍按对应规格执行，不能继承 Demo PASS。

#### Scenario: Demo MVP 满足完成条件
- **WHEN** 受影响聚焦测试和一次完整 Demo 均通过，且安全边界没有被放宽
- **THEN** Change 可以提交人工完成批准，不因缺少发布级证据继续扩建验证平台

### Requirement: 独立 Reviewer 必须按需使用
开发流程 SHALL 按需使用独立 Reviewer，不把它作为每个普通 Change 的必经步骤；其他已批准 Change 的明确复核要求 MUST 保留。需要复核时沿用现有只读职责、证据范围及原定完成批准，不扩大为新的流程或取消产品晋升要求。

#### Scenario: 普通改动无独立复核需要
- **WHEN** 本次普通修改及相关检查已完成，且没有用户或当前明确验收要求调用 Reviewer
- **THEN** 不因未调用 Reviewer 阻断完成摘要，仍保留既有人工完成批准

#### Scenario: 现有 Change 明确要求复核
- **WHEN** 某项已批准 Change 的原验收明确要求独立复核
- **THEN** 继续遵守该要求，不把按需约定解释为自动豁免

### Requirement: 外部引入的 Skill 必须保持只读
项目开发 SHALL 在自有指令和内容中维护项目规则；外部引入的 OpenSpec 及其他 Skill MUST 保持只读，不通过修改其正文或通用流程实施项目调整。

#### Scenario: 第三方默认流程与项目约定不同
- **WHEN** 项目需要自己的开发约定
- **THEN** 修改项目自有内容而非第三方 Skill，不能宣称第三方原始流程已被改变

### Requirement: 产品指令必须显式限定入口与阶段
根开发指令 SHALL 指向各产品入口的既有授权条件，不将有效组合输入描述为所有产品能力的统一前提。产品指令、Agent 配置及插件介绍 MUST 区分独立 Intake/交易记录/复盘、持仓或单股研究、研究综合与完整 fixture Council。仅完整 fixture Council 适用的组合动作、`NO_TRADE`、Risk 和 CIO 修订规则 MUST 带明确作用域，不覆盖研究阶段的 `RESEARCH_SYNTHESIS`、Risk=`NOT_RUN` 及禁止动作约束；更新说明不授予新能力或自动推进阶段。

#### Scenario: 非持仓单股与研究综合
- **WHEN** 用户请求现有非持仓单股入口或显式研究综合阶段
- **THEN** 指令不要求无关账户字段、不要求输出 `NO_TRADE` 或执行未开放的组合 Risk，不将研究判断升级为账户建议

#### Scenario: 独立产品入口
- **WHEN** 用户只调用 Intake、交易记录或复盘
- **THEN** 使用该入口的既有输入和权限约束，不自动调用 Council、不取得 CIO 权限、不启动产品研究 MCP

#### Scenario: 完整 fixture Council 兼容运行
- **WHEN** 运行明确属于完整 fixture Council
- **THEN** 保留原动作契约、Risk 否决与有限修订规则，旧 live 完整 Council 不因通用 CIO 文案重新开放

### Requirement: 配置维护必须保持用户确认范围
配置维护 SHALL 将项目行为规则、长期操作说明与本机历史事实分开。长期文档 MUST 不把过往任务的“本次授权”或“本轮未执行”当作当前授权/验收结论。用户级清理 SHALL 只修改已明确纳入方案且当前确实存在的弃用项，并保留其余配置及全局命令规则；配置存在不等于实际加载证明，菜单模型选择不改变产品锁。

#### Scenario: 清理已移除开关
- **WHEN** 按授权清理用户级已移除开关
- **THEN** 仅修改对应项并验证配置仍可解析，用户全局 Git 放行规则和其他插件、模型、权限设置不变，用户级文件不提交到项目

#### Scenario: 警告对应键当前不存在
- **WHEN** 历史 Guardian 警告对应的键在当前配置和 profile 中均不存在
- **THEN** 记录未复现及已有证据，不新增再删除该键、不改写无关配置，也不宣称已证明历史警告的根因

### Requirement: 开发规划必须对应最小可交付结果
开发 Agent SHALL 将用户目标转为最小可交付方案，在现有 Proposal 中说明可观察结果、关键修改/删除/保留对象、非目标和最小验收；批准前 SHALL 核对验收可行性并披露实际外部依赖。新增机制 MUST 说明当前必要性及既有能力为何不足，不因未来可能需要而扩建基础设施。批准后 MUST 保持范围和完成条件稳定；新增完成前置、改变规格或缩减交付须说明影响并获得批准，额外优化不自动成为阻断。

#### Scenario: 规划架构精简
- **WHEN** 用户要求删除自建控制职责并复用既有宿主
- **THEN** 方案说明实际退出的职责、执行路径与消费者，以及仍保留的业务边界；不得将文档整理、任务勾选或文件数量减少单独作为架构精简完成证明

#### Scenario: 验收依赖不可直接取得
- **WHEN** 最小验收依赖当前缺少的宿主能力、权限或用户动作
- **THEN** 批准前列明依赖、可独立交付部分和停止条件，不在实施后静默追加多宿主、真实运行或新平台作为完成前置

### Requirement: 需求调整必须先落盘且恢复必须读取当前规划
开始或恢复 Change 工作前，开发 Agent MUST 读取其当前 Proposal、Specs、Design、Tasks，先核对 Tasks“当前状态”，再读取本次所需证据。已确认且获相应规划修改授权的调整，若影响已约定行为、接口、数据契约、权限、验收或关键设计，MUST 在实现前更新实际受影响的 Specs、Design、Tasks并记录原因和影响；改变目标或范围时同时更新 Proposal。聊天讨论和规划更新 MUST NOT 被解释为新的 apply、真实运行、预算或发布授权；恢复工作不得继承旧聊天或其他 Change 的授权。

#### Scenario: 调整验收或数据契约
- **WHEN** 用户确认并授权更新相关需求
- **THEN** 先同步受影响规划和调整原因，再依据有效实施授权执行；未受影响文件无须为形式一致而重写

#### Scenario: 恢复已有任务
- **WHEN** 新会话接手或原会话恢复未完成 Change
- **THEN** 以当前规划和 Tasks 摘要核对范围、剩余项、阻断与授权，不从历史 PASS、旧窗口或聊天记忆推定当前可执行动作

#### Scenario: 修复不改变要求的普通错误
- **WHEN** 授权范围内发现路径、导入、类型或断言错误，修复仅恢复既定要求
- **THEN** 直接修复并执行受影响检查，不强制修改无关规划或逐步重新申请批准；不借普通修复改变安全门禁或完成标准

### Requirement: Tasks 必须维护唯一当前进度与交接摘要
每个 Change 的 `tasks.md`“当前状态” SHALL 是唯一当前进度与交接摘要，记录范围与授权边界、完成与剩余任务、阻断与未知、下一步、最新分层验收结论和证据链接，并与任务勾选及实际依据一致。其他文档 SHALL 引用该摘要而非平行维护现行进度；摘要不替代 Specs、Design、原始证据或实际授权。完成工作切片、发生阻断或授权变化、调整结束，以及暂停、交接或结束会话前，MUST 同步摘要和受影响验收结论，不要求每次工具调用新增状态文件、日志副本或全仓 hash 快照。

#### Scenario: 交接时存在阻断
- **WHEN** 会话准备暂停或交接，部分任务未完成
- **THEN** 当前摘要说明阻断影响的任务、最小解除条件、下一步和证据位置；未完成项保持未勾选，无依赖的已授权任务不被扩大阻断

#### Scenario: 更新已有验收结果
- **WHEN** 工作切片或获准调整完成并取得新验证结果
- **THEN** 在现有 Tasks 更新当前结论并引用原始依据，相关验收记录同步实际变化，不新建平行“当前状态”或重复证据包

### Requirement: 任务完成必须分层验证且历史不得回签
任务 MUST 达到其既定完成条件且有实际验证后才勾选；实现、测试、真实运行和人工批准 SHALL 分列，某一层通过不得替代其他明确要求，未执行、不适用或证据不足须如实说明。有效旧证据 SHALL 说明适用理由和证明范围，不声称本轮重跑。历史失败、未知和原始证据 MUST 按原时点保留，不补写、不回签；修复后以新实际验证更新当前结论。最终报告 SHALL 按“原目标 → 实际变化 → 验证证据”列明交付、未完成与阻断；OpenSpec strict、测试通过或任务勾选不得单独证明目标达成。

#### Scenario: 已实现但缺少既定真实验收
- **WHEN** 任务同时要求实现与真实运行，而当前只有实现和确定性测试证据
- **THEN** 分别记录已实现/测试通过和真实运行未完成，任务不勾选；实现任务本身未要求真实运行时，不为勾选自动追加该要求

#### Scenario: 历史失败后修复通过
- **WHEN** 新验证已解除旧失败或未知
- **THEN** 当前结论可引用新证据更新，旧失败/UNKNOWN/NOT_RUN及其时点保持，不将新结果回填为旧窗口成功

### Requirement: Claude 开发入口必须复用单一共享规则
Claude Code 根开发入口 SHALL 通过正式文件导入复用根 `AGENTS.md`，仅解释入口职责，不复制共享正文或自动加载全部专项文档、产品指令。该入口 MUST NOT 授予产品 CIO、产品运行、配置修改或 Git 发布权限。静态导入与文档检查 SHALL 仅声明结构检查范围，不作为实际宿主加载、权限强制或 Agent 遵循的证明。

#### Scenario: 检查根开发入口
- **WHEN** 检查根 `CLAUDE.md`
- **THEN** 正文包含代码围栏/行内代码之外的 `@AGENTS.md` 导入，目标存在；产品职责仍由原产品入口及阶段授权限定，无新 Hook、加载器或第二套开发规则

#### Scenario: 只有静态验证证据
- **WHEN** 根入口与规则结构检查通过但未观察新原生会话实际加载
- **THEN** 报告文档/结构通过和实际加载未验证，不自动启动模型会话补证，也不将文档存在当作加载或权限证明
