# 开发流程：仅在实施、验收或归档时读取

本文件属于开发控制面，不应用于产品 CIO 的运行收尾。模型/权限问题另见 [开发环境](environment.md)，具体运行命令见 [运行手册](../../reviews/runtime/runtime-replay-eval-runbook.md)。

## OpenSpec 职责与需求调整

开始或恢复 Change 前读取当前 Proposal、Specs、Design、Tasks，先核对 tasks.md“当前状态”，再读取本次所需证据；不把聊天记忆、旧窗口或其他 Change 的授权当作当前授权。最小方案及验收可行性按[根开发规则](../../AGENTS.md#目标规划与需求调整)处理。

| 内容 | 权威位置 |
| --- | --- |
| 目标、范围、非目标和最小验收 | Proposal |
| 行为、接口、数据、权限与验收要求 | Specs |
| 关键设计、取舍及调整原因 | Design |
| 任务勾选、唯一当前进度与交接摘要 | Tasks |
| 实际测试/运行、失败与验收依据 | 原始证据及已有验收记录，由 Tasks 引用 |

已确认并获相应规划修改授权的调整，先更新实际受影响的 Specs、Design、Tasks，目标或范围改变时同时更新 Proposal；在受影响规划中记录原因和影响，再按有效实施授权执行。只更新受影响内容，不为形式一致重写全部文件或另建调整摘要。未确认讨论不自动写入；规划更新不自动授予 apply、真实运行、预算增加或发布权限。

## 授权内持续实施

1. 行为变更先通过 OpenSpec propose/update 明确 Proposal、Specs、Design、Tasks；得到明确 apply 授权才实施。不顺手扩展其他需求。
2. 授权范围内连续实施、修复普通路径/导入/类型/断言错误并做受影响检查；仅恢复既定要求的修复无须重写无关规划或重新逐步批准。阶段汇报作为进度消息，随后继续，不逐步等待“继续”。仅诊断请求不授权修复。
3. 真实阻断包括新权限、关键用户选择、超出范围或预算、现有约束内无法解决的外部依赖。只暂停依赖它的工作，说明证据与最小用户动作；不自动提权、购买、修改系统配置或增加模型重试。
4. 环境错误与断言失败分开记录；失败证据保留，不用重复 LLM 调用排查确定性问题。沿用模型分工、已验证缓存与当前 Change 次数/费用/来源限制，见开发环境的模型节。

新增完成前置、修改既定规格、接受例外或缩减交付时，先说明原因、影响和安全边界并请求批准，不静默降低门禁；额外优化先作为建议，不自动成为阻断。原始证据不格式化、不补写；若格式检查命中其空白，需要明确分类和人工批准，不能豁免源码问题。

## 当前状态与交接

每个 Change 的 tasks.md只维护一个“当前状态”，建议置于任务前部；其他文档通过引用获取当前进度，不另维护平行摘要。摘要与勾选、实际批准和证据一致，但不替代规格、设计或原始依据。普通 Markdown 模板如下，不新增状态 Schema、工具或辅助文件：

```markdown
## 当前状态

- 更新：本次更新日期与时间。
- 范围与授权：引用当前规划；说明获准动作、预算、停止条件及未获准动作。
- 完成与剩余：引用任务编号，简述实际交付；未完成项保持未勾选。
- 验证与验收：分列实现、测试、真实运行、人工批准的最新结论及证据链接。
- 阻断与未知：受影响任务、依据和最小解除条件；无阻断则明确说明。
- 下一步：下一项可执行任务及前置条件。
```

完成工作切片、发生阻断或授权变化、调整结束，以及暂停、交接或结束会话前，同步当前状态和受影响验收记录的最新结论；不要求每次工具调用记录，不新增平行状态 MD/JSON、重复日志或全量 hash 副本。承载事实的契约及已有版本锁仍遵守根规则。

任务达到自身既定完成条件且有实际验证后才勾选，分列实现、测试、真实运行和人工批准；只要求任务既定的层级，不为所有任务追加真实研究。未执行、不适用或缺证据如实说明；旧证据复用须说明适用理由和证明范围，不冒称本轮重跑。历史 FAIL、UNKNOWN、NOT_RUN及原始证据按原时点保留，修复后用新验证更新当前结论，不回签旧运行或补勾未完成项。最终按“原目标 → 实际变化 → 验证证据”报告交付和缺口，不以 strict、测试数或任务勾选单独证明目标达成。

## Agent Package Milestone 0

零 LLM 装配 Demo 只通过显式 `python3 scripts/council-dev.py demo ...` 启动，用于观察 Agent Request/Response、Dispatch、PIT、只读 Tool Port、Risk 和最终报告的数据流。默认 `self-check` 不启动该 Demo；真实产品 Smoke 在用户所选的当前原生宿主产品会话另获授权，不由项目启动模型。宿主脚本只保留显式冻结 Replay 维护与已批准的 Tiger 严格只读入口。

Demo 验收只运行受影响的确定性测试和一次全链路合成演示。Runtime Eval、Execution Replay、Regression、Calibration、Ablation 与 Promotion 的源码和显式入口继续保留，但普通实现、Demo、差异复核或归档准备不得自动调用。Demo PASS 只证明装配和契约，不证明真实 LLM、Skill 推理、Subagent、主线程 CIO、live 研究或候选晋升。

apply 获批后，范围内实施、普通错误修复和聚焦检查持续推进；只有权限升级、破坏性操作、外部付费或凭证、范围/安全契约变化及真实阻断才中途暂停。最终归档和推送仍需要一次明确人工完成批准。

## 三层检查

### 研究输出接缝的复发预防

- 先按职责分类，再选修补：机械运输/固定身份由程序负责并用确定性正反例检查；权限与执行/研究状态检查服务端边界及原路径恢复；研究语义检查摘要、期间/单位、来源与每条关系，不能靠提示字符串断言宣布质量通过。新增案例应扩展对应类别，不为每个样本新增规则或 Agent。
- 参数指向的任务有权限，不等于调用方身份可信。共享只读 MCP 新增持久化副作用时，必须测试“合法目标 ID + 缺失/错误/另一任务凭据”是否在写入前拒绝且不占名额。任务专属 bearer 凭据只能防误路由，不是进程/会话身份认证；不要假设宿主提供了不存在的 caller identity。
- 回执须精确指向所提交内容，不仅是任务内序号。凭据只留在授权本地私有 packet 和对应任务交付；普通 Hook/MCP 审计只存 hash，不输出凭据。宿主原始工具调用转录可能含参数，仍属私有运行材料，不得直接提交或发布。历史协议只读兼容与允许新写入应分别说明和测试。

- 工具可见不等于任务授权：共享MCP增加专用工具时，工具描述和实际任务上下文必须同时说明适用条件、未启用任务的原提交方式；保留服务端拒绝，并验证“被拒之后仍可沿原路径正常提交”。不要为消除误用直接扩大权限。
- 执行失败、来源不足、研究充分性分开：提交工具拒绝不自动意味着没有研究；实际取证失败仍须保留影响。Schema允许某个状态组合，不代表模型选择该状态的理由正确。
- 校验摘要与正文，而不只查数字是否出现：同一窗口/基准/单位的方向和幅度应一致。真实反例是正文领先209.82个百分点、摘要却称“小幅跑赢”；不要把该样本数值写进产品提示或编码形容词阈值。
- 合法引用不等于关系成立：逐项看document→target claim→resulting claim；收购事实不能支持“独立研报覆盖不足”。不要仅测ID存在，也不要由Python自动删改语义关系。
- 每次修补保留原失败证据，在受影响的实际交付路径上验证指引、权限拒绝、旧路径和输入不变性；两条路径均受影响或既定规格明确要求时仍覆盖两条，不豁免原要求。零模型测试只证明交付及契约；语义效果须真实研究和内容复核，不能用提示字符串断言冒称质量通过。

这些是开发检查原则，不新增运行时评分器、Agent或重试循环。最新案例及证据见[八维消费验收记录](../../reviews/development/complete-eight-dimension-source-consumption-acceptance.md)。

- 日常开发：纵向切片使用任务声明的受影响聚焦验证，保留输入、实际命令、输出和所需完整 hash；hash用于对应证据/版本定位，不默认扩成每轮全仓快照。验证不完整不勾选，不把 Change 收尾、完整产品运行或发布级证明作为每步前置。
- Change 验收：开始时写明对应规格、实际差异、受影响依赖、旧证据标识/适用理由和缺口，只补受影响且无有效证据的项目。修改产品启动或加载行为须有受影响的真实 Smoke；仅开发文档和 Reviewer 规则改变只检查相应文档/配置。
- Change 实现完成：满足当前 Change 明确的规格、任务、按需独立评审及人工批准。apply 授权、阶段汇报或 Reviewer PASS 不等于人工完成批准；历史基线不足不等于当前实现失败。小 Change 通过不能替代尚未完成的股票验收。
- 候选晋升：独立满足版本锁、OpenSpec 校验、完整确定性测试、Eval/Regression、架构评审及人工批准。Evidence/PIT/Risk/Schema/Trace 硬门禁不能由平均分覆盖。
- `CHANGE_REVIEW: PASS` 可与 `CANDIDATE_PROMOTION: NOT_PROMOTABLE` 并存，不得因此修改生产版本指针。历史 Replay/Ablation 不能包装为新候选晋升证据。
- 未修改相关能力时，不默认重复 Calibration、Ablation、Promotion；如当前规格明确要求更广验收，先透明提出调整供批准，而非自行忽略。

独立 Reviewer 按日常差异、Change 验收或候选晋升的目的读取实际增量、规格、事件、底层产物及完整 hash，不仅复述 PASS；非晋升复核不默认索取生产批准。保留只读权限，缺证据列出具体理由交主开发按授权处理，不自行启动产品、完整 Gate 或项目沙箱。只读 Reviewer 将结果返回主线程落盘，不为写报告增加权限。

## 归档和 Git 发布

仅开发收尾执行：保存人工批准和证据标识 → OpenSpec 归档与主规格同步 → 检查差异、工作区、敏感信息和已审阅范围 → scoped commit → push 到根 AGENTS.md 指定远端。

每次成功归档必须完成相应提交/推送；但校验失败、测试失败、未审阅实现或疑似敏感信息未处理时停止发布。不得使用全目录暂存将其他 Change 或私密状态带入提交，不 force push。

暂停的 Change 保留任务状态、未提交修改和原始证据，不归档、回退或勾选未完成项。工作现场清单/hash 只用于防止误改，不是产品版本锁或新晋升门禁。共享文件按本次 hunk 分离，既有无关暂存内容不得夹带；无法安全分离则停止提交。按用户指定收尾后，重读生效 AGENTS.md、开发流程和原 Change 的 Proposal/Specs/Design/Tasks，再恢复原未完成项；不得改写旧锁或降低原验收标准。

`.codex-runtime`、凭据、私人会话及未脱敏环境信息只留在授权本地环境。发布记录必须说明排除范围；若排除改变完整目录可重算性，保留原 hash 并明确 Git 副本的限制，不编造缺失文件。提交完成报告 commit、push 和剩余工作区状态，不把提交等同于生产晋升。
